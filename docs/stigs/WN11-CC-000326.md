**STIG-ID:** WN11-CC-000326 | **Rule-ID:** SV-253414r958422_rule
**Severity:** CAT II | **CCI:** CCI-000135 | **NIST 800-53:** AU-3(1)

## Objective
Remediate DISA STIG WN11-CC-000326, which requires PowerShell script block logging to be enabled. Confirm with an authenticated Tenable compliance scan.

## Problem Statement
Without script block logging, PowerShell attacks — encoded commands, fileless/in-memory execution, living-off-the-land tradecraft — leave little to no forensic trace. Script block logging records the actual code PowerShell executes (Event ID 4104), including de-obfuscated content, giving defenders visibility into what an attacker actually ran. This is a detection-enabling control: it does not block the attack, it makes the attack visible. CAT II, NIST AU-3(1).

## Environment
- **Target:** Windows 11 Pro VM (`VirtualTest15`), private IP 10.0.0.10, Azure Cyber Range subscription
- **Scanner:** Tenable `LOCAL-SCAN-ENGINE-01`, authenticated credentialed scan
- **Audit policy:** DISA Microsoft Windows 11 STIG v2r7 (Windows Compliance Checks)

## Solution / Steps Taken
1. Confirmed the finding in the baseline authenticated scan — **Failed**.
2. Reviewed the Tenable Solution text: set `EnableScriptBlockLogging` to `1` under the ScriptBlockLogging policy key.
3. Applied the fix via PowerShell (elevated):

```powershell
New-Item -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" -Force | Out-Null
New-ItemProperty -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" -Name "EnableScriptBlockLogging" -PropertyType DWord -Value 1 -Force
```

4. Verified the value persisted, then re-scanned — **Passed**.

## Key Findings
- Registry path: `HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging`
- Value: `EnableScriptBlockLogging` (DWORD) — compliant when `1`
- Once enabled, PowerShell writes executed script blocks to **Event ID 4104** (Microsoft-Windows-PowerShell/Operational).

## Security and SOC Relevance
This is the control that directly connects my vulnerability-management work to detection engineering and threat hunting. Enabling script block logging produces Event ID 4104, which is the primary data source for hunting encoded/obfuscated PowerShell (ATT&CK T1059.001) — a technique I also build detections for in my Splunk lab (Stage 2). Remediating this STIG is not just a compliance checkbox; it turns on the telemetry a SOC needs to catch one of the most common attacker tools on Windows.

## Challenges and How I Solved Them
Applied the established key-creation pattern (`New-Item -Force` then `New-ItemProperty -Force`) since the ScriptBlockLogging key was absent by default. Fix applied and validated on the first cycle.

## Lessons Learned
Some STIGs are preventive and some are detective. This one is detective — it does not stop an attack, it ensures the attack is logged. Understanding that distinction is exactly what separates a checkbox remediation from understanding *why* a control exists, which is the framing I bring into detection engineering.
