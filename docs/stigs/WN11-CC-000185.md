## Objective
Remediate DISA STIG WN11-CC-000185, which requires the default autorun behavior to be configured to prevent autorun commands. Confirm with an authenticated Tenable compliance scan and document a full fix → revert → re-apply validation cycle.

> **Note:** This control was selected as a substitute for WN11-CC-000391 (Internet Explorer must be disabled), which could not be remediated on this build. See the companion note `WN11-CC-000391-NOT-APPLICABLE.md` for the rationale.

## Problem Statement
Autorun automatically executes commands defined on removable media and network shares when they are mounted. This is a classic malware-propagation vector — a malicious USB or share can trigger code execution the moment it is connected. Preventing autorun commands blocks this automatic-execution path. This is a **CAT I** (highest severity) control, mapped to NIST CM-7(2).

## Environment
- **Target:** Windows 11 Pro VM (`VirtualTest15`), private IP 10.0.0.10, Azure Cyber Range subscription
- **Scanner:** Tenable `LOCAL-SCAN-ENGINE-01`, authenticated credentialed scan
- **Audit policy:** DISA Microsoft Windows 11 STIG v2r7 (Windows Compliance Checks)

## Solution / Steps Taken
1. Confirmed the finding in the baseline authenticated scan — **Failed**.
2. Reviewed the Tenable Solution text: set `NoAutorun` to `1` under the Explorer policy key.
3. Applied the fix via PowerShell (elevated):

```powershell
New-Item -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\Explorer" -Force | Out-Null
New-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\Explorer" -Name "NoAutorun" -PropertyType DWord -Value 1 -Force
```

4. Verified the value persisted (`NoAutorun : 1`), then re-scanned — **Passed**.

## Key Findings
- Registry path: `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\Explorer`
- Value: `NoAutorun` (DWORD) — compliant when `1`
- **CAT I** — highest-severity control in this remediation set.

## Security and SOC Relevance
Disabling autorun addresses one of the most durable malware-delivery techniques (removable-media autorun, ATT&CK T1091 Replication Through Removable Media). As a CAT I finding, it is exactly the kind of high-priority misconfiguration a VM Analyst escalates and remediates first.

## Challenges and How I Solved Them
This control was chosen mid-project as a replacement for WN11-CC-000391. During remediation of 000391 I found that the standard registry fix did not satisfy the audit, and the documented DISA fallback (`Disable-WindowsOptionalFeature -FeatureName Internet-Explorer-Optional-amd64`) failed with "feature name unknown" — because Internet Explorer 11 is already retired/removed in Windows 11 25H2, making the feature invalid on this build. Rather than spend disproportionate time on an environment-limited control, I documented 000391 as not-applicable and substituted WN11-CC-000185 (a CAT I control) to complete a full, defensible set of ten. The substitution actually strengthened the set by adding a highest-severity finding.

## Lessons Learned
Sound VM work includes knowing when a control is environment-limited and making a documented judgment call rather than forcing an invalid fix. Recognizing that an OS build had already removed the feature the STIG targeted — and substituting an equivalent-or-higher-severity control — is the kind of scoping decision a real vulnerability-management program requires.
