# WN11-CC-000175 — Application Compatibility Program Inventory Must Be Prevented

## Objective
Remediate DISA STIG WN11-CC-000175, which requires that the Application Compatibility Program Inventory be prevented from collecting data and sending it to Microsoft. Confirm with an authenticated Tenable compliance scan.

## Problem Statement
The Application Compatibility Inventory Collector gathers data about installed applications and transmits it to Microsoft. On a controlled asset this is an uncontrolled outbound telemetry channel that leaks software inventory — useful reconnaissance if intercepted and an unnecessary egress path. Disabling the collector closes it. CAT III, NIST CM-7a.

## Environment
- **Target:** Windows 11 Pro VM (`VirtualTest15`), private IP 10.0.0.10, Azure Cyber Range subscription
- **Scanner:** Tenable `LOCAL-SCAN-ENGINE-01`, authenticated credentialed scan
- **Audit policy:** DISA Microsoft Windows 11 STIG v2r7 (Windows Compliance Checks)

## Solution / Steps Taken
1. Confirmed the finding in the baseline authenticated scan — **Failed**.
2. Reviewed the Tenable Solution text: set `DisableInventory` to `1` under the AppCompat policy key.
3. Applied the fix via PowerShell (elevated):

```powershell
New-Item -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\AppCompat" -Force | Out-Null
New-ItemProperty -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\AppCompat" -Name "DisableInventory" -PropertyType DWord -Value 1 -Force
```

4. Verified the value persisted, then re-scanned — **Passed**.

## Key Findings
- Registry path: `HKLM\SOFTWARE\Policies\Microsoft\Windows\AppCompat`
- Value: `DisableInventory` (DWORD) — compliant when `1`

## Security and SOC Relevance
Disabling the inventory collector removes an uncontrolled telemetry egress that leaks the endpoint's software inventory. Limiting outbound data flows and reducing reconnaissance exposure is core least-functionality hardening a VM Analyst validates.

## Challenges and How I Solved Them
Standard application of the key-creation pattern (`New-Item -Force` then `New-ItemProperty -Force`) since the `AppCompat` policy key was absent by default. No control-specific issues; the fix applied and validated cleanly on the first cycle.

## Lessons Learned
By this point in the remediation set the create-key-then-set-value pattern was proven and repeatable, which made the remaining registry-based controls fast and predictable to remediate.
