# WN11-CC-000315 — Windows Installer "Always install with elevated privileges" Must Be Disabled

**Project:** Project Basilio — DISA STIG Remediation (LOGN Pacific Cyber Range Internship)
**Date:** June–July 2026
**Stage:** Vulnerability Management — STIG Remediation
**Tools:** Tenable Vulnerability Management, PowerShell, Azure (Windows 11 VM)
**Benchmark:** DISA Microsoft Windows 11 STIG v2r7
**STIG-ID:** WN11-CC-000315 | **Vuln-ID:** V-253411 | **Rule-ID:** SV-253411r1051054_rule
**Severity:** CAT II | **CCI:** CCI-001812, CCI-003980 | **NIST 800-53:** CM-11(2)

---

## Objective
Remediate DISA STIG WN11-CC-000315 on a Windows 11 asset, which requires that the Windows Installer feature "Always install with elevated privileges" be disabled. Confirm the fix with an authenticated Tenable compliance scan, prove the remediation is effective by reverting and re-applying, and document the full cycle as verifiable evidence.

## Problem Statement
When "Always install with elevated privileges" is enabled, Windows Installer runs any package with SYSTEM-level privileges regardless of the invoking user's rights. A standard or compromised user could craft a malicious MSI and gain full local privilege escalation. Disabling this setting closes a well-known escalation path and is a CAT II control tied to NIST CM-11(2) (user-installed software restrictions).

## Environment
- **Target:** Windows 11 Pro VM (`VirtualTest15`), private IP 10.0.0.10, Azure Cyber Range subscription
- **Scanner:** Tenable `LOCAL-SCAN-ENGINE-01`, authenticated credentialed scan
- **Audit policy:** DISA Microsoft Windows 11 STIG v2r7 (Windows Compliance Checks)
- **Scan template:** `BT_Win11_STIG_Template_FAST_SCAN` (compliance-only, scoped for fast rescans)

## Solution / Steps Taken
1. Confirmed the finding in the baseline authenticated scan — WN11-CC-000315 returned **Failed**.
2. Reviewed the Tenable Solution text and DISA reference: set `AlwaysInstallElevated` to `0` (Disabled) under the Windows Installer policy key.
3. Applied the fix via PowerShell (elevated) on the target VM:

```powershell
New-Item -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\Installer" -Force | Out-Null
Set-ItemProperty -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\Installer" -Name "AlwaysInstallElevated" -Value 0 -Type DWord
```

4. Re-ran the compliance scan — WN11-CC-000315 returned **Passed**.
5. **Reverted** to prove the remediation is what drives compliance:

```powershell
Set-ItemProperty -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\Installer" -Name "AlwaysInstallElevated" -Value 1 -Type DWord
```

6. Re-ran the scan — returned **Failed**, confirming the control depends on this exact setting.
7. **Re-applied** the fix (step 3) and re-scanned — returned **Passed**.

## Validation and Testing
Full fix → revert → re-apply cycle, each state confirmed by a separate authenticated Tenable scan:

| Scan State | Registry Value | Audit Result |
|---|---|---|
| Baseline | key absent / `1` | **Failed** |
| After fix | `0` | **Passed** |

Scan timestamps for all runs are captured in the Tenable **History** tab (see Evidence), which serves as the tamper-evident audit trail proving each state is a distinct scan.

## Key Findings
- Registry path: `HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer`
- Value: `AlwaysInstallElevated` (DWORD) — compliant when `0`
- Mapped to NIST 800-53 CM-11(2), CCI-001812 / CCI-003980, CAT II
- The compliant state requires the value explicitly set to `0`; an absent key also fails, so the fix must create the key if it does not exist.

## Security and SOC Relevance
This is a direct local privilege-escalation control. In a real VM Analyst workflow, this is exactly the type of misconfiguration a compliance scan surfaces and that must be remediated and re-validated — not just patched and assumed fixed. The revert-and-reconfirm step mirrors how an analyst proves to an auditor or ISSO that a remediation is effective and durable, not coincidental.

## Challenges and How I Solved Them
The initial credentialed scan returned a single Warning instead of Pass/Fail results. I diagnosed this as an authentication failure: local admin accounts have their token filtered over the network by UAC, so Tenable could authenticate but not read the registry. I resolved it by setting `LocalAccountTokenFilterPolicy = 1`, enabling Remote Registry / admin shares / Server service in the scan template, and disabling the host firewall — after which the full DISA audit returned ~263 Pass/Fail results.

## Lessons Learned
Verifying remediation at the source (reading the registry value directly with `Get-ItemProperty`) rather than trusting a command's exit status is essential — a `Set-ItemProperty` can report success without persisting. The revert-to-prove step is what turns "I changed a setting" into "I demonstrated this setting controls the compliance state."
